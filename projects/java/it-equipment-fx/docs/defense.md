# Как объяснить проект на защите

## Путь от кнопки до базы

Пример: пользователь сохраняет новую заявку.

1. `request-form.fxml` описывает ComboBox сотрудника, поля и кнопку. `fx:controller` указывает Java-класс. `fx:id` связывает элементы с его полями `@FXML`; `onAction="#save"` вызывает метод `save`.
2. `RequestFormController` читает значения и показывает ошибки рядом с формой. В ComboBox хранится объект `User`, а имя используется только для отображения. ID получается из выбранного объекта.
3. `FormSupport` блокирует повторное сохранение и запускает фоновую работу через `FxTasks`.
4. `RequestService.create` повторно проверяет данные, существование сотрудника и бизнес-правила. Поэтому обход формы не позволяет обойти правила.
5. `JdbcRequestRepository` получает `Connection` из `DatabaseManager`, создаёт `PreparedStatement`, заполняет параметры и выполняет запрос.
6. PostgreSQL проверяет ограничения и сохраняет запись. Репозиторий читает возвращённые значения через `ResultSet` и создаёт модель.
7. При успехе форма закрывается, главное окно повторно загружает данные. При ошибке введённые значения остаются в форме.

SQL находится в repository, обработчик кнопки обращается к сервису. Окно не знает деталей запроса и структуры ResultSet.

## Объекты, инкапсуляция и полиморфизм

`User` — сотрудник, `EquipmentRequest` — заявка на оборудование. Поля закрыты модификатором `private`. Конструктор задаёт состояние, геттеры позволяют прочитать его. Модели неизменяемы: изменение записи создаёт новый объект.

Сервисы принимают интерфейсы репозиториев. При обычном запуске используются JDBC-реализации. В модульных тестах те же вызовы обслуживают реализации в памяти. Это полиморфизм: один контракт, разные реализации. Интерфейс также позволяет позже изменить способ хранения без переписывания правил.

`RequestStatus` и `EquipmentType` — enum: набор допустимых значений ограничен. `RequestStatus.canTransitionTo` описывает переходы, а не только названия статусов.

## FXML и CSS

FXML — декларативное описание дерева элементов окна. FXMLLoader создаёт объекты, внедряет поля и вызывает `initialize`. В `main.fxml` вложенные вкладки подключаются через `fx:include`. FXMLLoader также предоставляет их контроллеры в полях с суффиксом `Controller`.

CSS задаёт цвета, отступы, кнопки, таблицы и сообщения ошибок. Контроллер координирует действия, сервис проверяет правила; перенос цвета в CSS не меняет бизнес-логику.

## Коллекции, поиск и сортировка

Снимок базы хранится в `DashboardData` как списки. `ObservableList` уведомляет JavaFX об изменениях. `FilteredList` оставляет строки, удовлетворяющие `RequestFilter`. Текст и два выбранных enum-фильтра объединены условием «И». `SortedList` связан с компаратором TableView, поэтому сортировка меняется при нажатии заголовка.

Сортировка количества выполняется по Integer, времени — по LocalDateTime. Дата форматируется только для отображения. Если превратить числа в строки до сортировки, «10» может оказаться перед «2».

Поиск и статистика сейчас выполняются по загруженным спискам: этого достаточно для учебного набора. Для большой базы потребуются серверные фильтры и постраничная загрузка.

## Потоки

Элементы JavaFX изменяются в JavaFX Application Thread. Долгая работа JDBC и Excel выполняется в `Task` в отдельном потоке. `setOnSucceeded` и `setOnFailed` возвращают результат в поток интерфейса. Пока идёт сохранение, форма заблокирована. После ошибки блокировка снимается и отображается понятное сообщение.

Нельзя напрямую менять TableView из метода `Task.call`: это другой поток. Не следует выполнять JDBC в обработчике кнопки синхронно — окно будет ждать базу и перестанет реагировать.

## JDBC и ограничения

`Connection` представляет соединение; `PreparedStatement` — SQL-шаблон с параметрами; `ResultSet` — результат SELECT или RETURNING. `try-with-resources` закрывает эти ресурсы даже при исключении.

В `Statement` часто передают готовую SQL-строку. В `PreparedStatement` значения передаются отдельно (`setString`, `setLong`); кавычки пользовательского текста не становятся SQL-командами. Само использование PreparedStatement не защитит запрос, если сначала склеить его с пользовательским вводом.

Таблицы связаны: `equipment_requests.user_id → users.id`. PK идентифицирует запись, FK требует существующего сотрудника, NOT NULL запрещает отсутствие обязательных данных, UNIQUE ограничивает email, CHECK проверяет количество и значения enum.

Смена статуса в репозитории учитывает ожидаемый старый статус. Если другой клиент уже поменял его, обновление не должно молча перезаписать новый результат. Не все операции являются общей транзакцией: обновление снимка сотрудников и заявок выполняется отдельными чтениями.

## Исключения и экспорт

`BusinessException` сообщает о нарушении правила, `EntityNotFoundException` — об отсутствующей записи, `DataAccessException` оборачивает ошибку хранения. `Ui.message` преобразует техническую ошибку в объяснение, включая отказ входа PostgreSQL. Пароль и stack trace в диалоге не показываются.

Excel создаётся Apache POI. `FileChooser` возвращает выбранный пользователем путь. Перед фоновой записью берётся копия текущих строк таблицы: последующее изменение интерфейса не должно менять состав выгрузки. Сначала книга формируется во временном файле, затем заменяет целевой файл. В `finally` временный файл очищается.

## Docker под капотом

Compose описывает контейнер PostgreSQL, порт, том, SQL и проверку готовности. Windows-клиент подключается к `localhost:55433`; Docker перенаправляет соединение на порт `5432` контейнера. Имя `db` предназначено для контейнерной сети и не используется клиентом Windows.

Именованный том хранит файлы PostgreSQL независимо от контейнера. Инициализационные SQL исполняются только для пустой базы. JavaFX и его JVM работают отдельно на Windows, поэтому закрытие JavaFX не останавливает PostgreSQL.

## Сценарий демонстрации

Откройте список заявок, найдите сотрудника, совместите фильтры статуса и оборудования. Отсортируйте по количеству и дате. Создайте заявку, покажите ошибку количества, исправьте её, сохраните. Измените новую заявку, одобрите её и объясните, почему редактирование стало недоступно. Покажите отмену удаления, статистику и экспорт отфильтрованных строк. Для удаления выбирайте отдельную тестовую новую заявку.

Для самостоятельной тренировки напишите короткий enum, интерфейс репозитория, конструктор с private-полями и JDBC-метод SELECT по ID с `?`, `setLong` и `try-with-resources`. На защите важно объяснить эти конструкции своими словами.

## Каскадное удаление

Внешний ключ equipment_requests.user_id ссылается на users.id с ON DELETE CASCADE. UserService проверяет существование сотрудника и вызывает репозиторий. Репозиторий выполняет один DELETE FROM users WHERE id = ?. PostgreSQL сам удаляет связанные заявки любого статуса в той же транзакции. Отдельный цикл удаления в Java не нужен. При отмене диалога запрос вообще не отправляется. После успешного удаления главное окно заново читает данные, поэтому таблица заявок и статистика также обновляются.

Для существующей базы применяется 03-cascade-delete.sql: DROP CONSTRAINT и ADD CONSTRAINT находятся между BEGIN и COMMIT. Это изменение схемы, а не очистка таблиц. При удалении одной заявки пользователь и другие заявки сохраняются: каскад направлен от сотрудника к заявкам.

## Автоматическая миграция Compose

Сервис migrate зависит от db с condition: service_healthy. Проверка PostgreSQL использует TCP, чтобы не принять временный сервер инициализации за готовую базу. После готовности psql применяет миграцию с ON_ERROR_STOP=1. restart: no означает, что успешно завершившуюся одноразовую задачу не нужно постоянно перезапускать. Docker Compose запускает серверную часть; окно JavaFX запускается run.cmd на Windows.
