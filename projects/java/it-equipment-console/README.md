# Заявки на выдачу IT-оборудования

Консольная информационная система для КР 1. Java 17+, Maven, PostgreSQL 16, JDBC, Apache POI. Интерфейс — на русском языке. Основные данные сохраняются в PostgreSQL между запусками.

## Быстрый запуск через Docker Compose

Нужен **Docker Desktop** с запущенным движком Linux containers. Java, Maven и PostgreSQL на компьютере устанавливать не требуется: Java 17 и база запускаются в контейнерах. Распакуйте архив полностью и откройте `run.cmd`. Или выполните в папке проекта:

```powershell
docker compose run --build --rm app
```

При первом запуске Docker скачает образы PostgreSQL и Java и соберёт образ приложения со шрифтами для Excel-экспорта. Затем создаст базу, дождётся её готовности и покажет меню. Пункт `0` завершит приложение; база продолжит работать. Повторный запуск — той же командой или через `run.cmd`. Первый запуск требует интернета; последующие сборки используют кеш Docker.

Для Windows Terminal используйте UTF-8: `chcp 65001`. Файл `run.cmd` делает это автоматически. Excel-файлы из пункта 7 будут находиться в папке `exports` на компьютере.

Docker создаст базу `it_equipment`, таблицы, 5 сотрудников и 10 заявок. Том сохраняет данные. Скрипты из `sql/` выполняются **только при первом создании пустого тома**. Остановка без удаления данных: `docker compose down` (без флага `-v`). Приложение обращается к `db:5432` внутри сети Compose. Порт базы не публикуется на Windows, поэтому локальная PostgreSQL не конфликтует с контейнером.

Проверка состояния и журнал базы:

```powershell
docker compose ps
docker compose logs db
```

Если ранее уже создавали том этого проекта с другим паролем, новые настройки не меняют пароль внутри существующей базы. Для стандартного пользователя проекта выполните:

```powershell
docker compose exec db psql -U it_app -d it_equipment -c "ALTER ROLE it_app WITH PASSWORD 'it_demo_password';"
```

Не удаляйте том с существующими данными для исправления пароля.

## Запуск с установленной PostgreSQL без Docker

Этот вариант требует Java 17+. Готовый JAR запускается командой `java -Dfile.encoding=UTF-8 -jar it-equipment-1.0.0.jar`. Для пересборки исходников нужен Maven 3.9+: `mvn clean package`; результат будет в `target/`. Чтобы контейнер использовал пересобранную версию, скопируйте этот JAR в корень проекта.

В `psql` под администратором выполните отдельно, вне транзакции:

```sql
CREATE ROLE it_app LOGIN PASSWORD 'it_demo_password';
CREATE DATABASE it_equipment OWNER it_app;
```

Затем из корня проекта:

```powershell
psql -h localhost -U it_app -d it_equipment -v ON_ERROR_STOP=1 -f sql/01-schema.sql
psql -h localhost -U it_app -d it_equipment -v ON_ERROR_STOP=1 -f sql/02-seed.sql
```

Схема и начальные данные устанавливаются один раз в пустую базу. Повторное выполнение не предназначено для обновления существующей БД. Для создания отдельной БД администратором также приложен `sql/create-database.sql`.

Для локального запуска Java задайте переменные в том же окне PowerShell (Compose самостоятельно задаёт адрес `db` для контейнера):

```powershell
$env:DB_URL='jdbc:postgresql://localhost:5432/it_equipment'
$env:DB_USER='it_app'
$env:DB_PASSWORD='it_demo_password'
```

Пароль в примере предназначен для локальной учебной базы. В коде меню нет SQL. Приложение не создаёт и не очищает базу автоматически. При ошибке БД меню выводит сообщение и продолжает работу.

## Возможности меню

1. Сотрудники: список, получение по ID, создание, изменение, удаление.
2. Заявки: список, получение по ID, создание, изменение, смена статуса, удаление с подтверждением.
3. Поиск: по части обоснования или ФИО сотрудника, без учёта регистра.
4. Фильтрация: по статусу или типу оборудования.
5. Сортировка: по дате создания или количеству, по возрастанию; ID разрешает равенство значений.
6. Статистика: число сотрудников, число заявок, сумма единиц оборудования, количество заявок каждого из пяти статусов.
7. Excel: два листа «Заявки» и «Сотрудники», заголовки, автофильтры, закрепление первой строки, числовые количества и даты.
8. Вывод обеих таблиц базы.
0. Выход (в подменю — возврат).

Файлы выгрузки создаются в `exports/` с датой и временем в имени. Существующий файл не перезаписывается. Для экспорта из БД без меню:

```powershell
docker compose run --build --rm app --export exports/report.xlsx
```

В `examples/equipment-demo.xlsx` приложен экспорт тестовых данных из PostgreSQL.

## Бизнес-правила

- ФИО, email, отдел и обоснование обязательны, их длина ограничена.
- Email проверяется, приводится к нижнему регистру; уникальность обеспечивает БД.
- В заявке должен быть существующий сотрудник.
- Тип оборудования выбирается из `EquipmentType`; количество — от 1 до 10.
- Новая заявка создаётся только со статусом `NEW`.
- Переходы: `NEW → APPROVED / REJECTED / CANCELLED`, `APPROVED → ISSUED / CANCELLED`. Остальные статусы конечные. Повторный переход в тот же статус запрещён.
- Менять сотрудника, оборудование, количество и обоснование можно только у новой заявки.
- Удалять можно новые, отклонённые и отменённые заявки. Одобренные и выданные сохраняются.
- Нельзя удалить сотрудника, у которого есть заявки: внешний ключ `ON DELETE RESTRICT`.

Проверки находятся в сервисах и `RequestStatus`; основные ограничения данных продублированы в БД. Изменение статуса использует условный `UPDATE` с предыдущим статусом, поэтому два одновременных перехода не перезапишут друг друга. Прямое администрирование БД не подчиняется сервисному графу переходов.

Программа учитывает заявки, а не складские остатки: выдача означает изменение статуса. Серийные номера устройств, резервирование склада, роли и авторизация не входят в этот вариант КР 1.

## Архитектура и ООП

```text
Main (связывает объекты)
  → ConsoleUi (ввод и вывод)
    → UserService / RequestService (правила)
      → UserRepository / RequestRepository (интерфейсы)
        → JdbcUserRepository / JdbcRequestRepository
          → DatabaseManager → PostgreSQL
```

Модели `User` и `EquipmentRequest` — неизменяемые объекты с `private final` полями, конструкторами и геттерами. Изменение записи создаёт новый объект; произвольные сеттеры не позволяют обходить правила. `RequestStatus` и `EquipmentType` — enum. Сервисы получают интерфейсы репозиториев через конструкторы: это полиморфизм и возможность заменить реализацию. В тестах используются реализации в памяти, в приложении — исключительно JDBC.

`List`, `Map`, `Set`, `Comparator` и Stream API используются для поиска, сортировки и статистики. Для объёма учебной БД поиск и фильтрация выполняются над прочитанной коллекцией; для большой БД их следует перенести в SQL с пагинацией.

`BusinessException` описывает нарушение правила, `EntityNotFoundException` — отсутствие записи, `DataAccessException` — ошибку JDBC. `Connection`, `PreparedStatement`, `ResultSet` закрываются через try-with-resources. Все пользовательские значения SQL передаются параметрами `?`.

ER-диаграмма: `docs/er-diagram.svg` (открывается браузером), исходник Mermaid — `docs/er-diagram.mmd`. Связь — один сотрудник может иметь ноль или много заявок; каждая заявка принадлежит одному сотруднику.

## Проверки

```powershell
mvn test
```

Без переменной `TEST_DB_URL` выполняются модульные тесты, интеграционный тест пропускается. Для теста с PostgreSQL сначала установите схему в отдельную тестовую базу, затем:

```powershell
$env:TEST_DB_URL='jdbc:postgresql://localhost:5432/it_equipment_test'
$env:DB_USER='it_app'
$env:DB_PASSWORD='it_demo_password'
mvn test
```

Интеграционный тест проверяет JDBC CRUD, уникальность email, внешний ключ, ограничение количества, условную смену статуса и чтение созданного Excel. Созданные им записи удаляются в `finally`; последовательности ID при этом могут иметь пропуски, что нормально.

Материалы для защиты и распределение работы на четверых — в `docs/defense.md`. Фактически выполненные проверки — в `docs/verification.md`.
