# Warehouse-66 — Система складского учёта

Многофункциональное клиент-серверное веб-приложение для автоматизации складского учёта на предприятии. Курсовая работа по дисциплине «Создание программного обеспечения» (СПО-2), задание №66.

Полный стек: **PostgreSQL 16 + Node.js 20 / Express.js 4 + React 18 / Vite 5 + Docker**. Бизнес-логика вынесена в пакет процедур и функций на **PL/pgSQL**, аудит операций ведётся автоматически через триггеры.

## Описание

Складской учёт — одна из базовых задач корпоративных информационных систем: от точности учёта поступлений, хранения и движения материалов зависит планирование закупок и обоснованность управленческих решений. Современный склад оперирует сотнями товарных позиций и десятками поставщиков, что делает ручной учёт трудоёмким и склонным к ошибкам.

Цель проекта — разработать веб-приложение, которое:

- ведёт нормализованный учёт поступлений материалов с полным набором реквизитов (поставщик, документ, балансные счета, цена, количество);
- демонстрирует приёмы программирования на стороне СУБД — пакет PL/pgSQL и три триггера;
- выполняет аналитические запросы (поставщики материала, поставщики по городу банка, топ по объёму);
- поддерживает WMS-функции (перемещение ордеров между складами, инвентаризация остатков);
- разграничивает доступ по трём ролям (`admin` / `client` / `guest`) через JWT;
- разворачивается одной командой `docker compose up --build`.

В отличие от коммерческих аналогов («1С: Управление торговлей», «МойСклад», Odoo Inventory), решение целенаправленно ориентировано на демонстрацию полного цикла разработки: проектирование реляционной БД, программирование на PL/pgSQL, REST API на Node.js, SPA на React и контейнеризация.

## Возможности

**Главный экран**

- Просмотр четырёх складов в виде карточек с прогресс-баром загрузки и цветовой индикацией: зелёный < 20% / жёлтый 20–49% / оранжевый 50–79% / красный >= 80%
- Журнал операций в правой панели с авто-обновлением каждые 5 секунд (формируется триггерами БД)
- Шесть кнопок действий в нижней панели с разграничением по ролям

**Поставка товаров** (client, admin)

- Форма из 11 полей со справочниками поставщиков, материалов, документов и единиц измерения
- Авто-подстановка единицы измерения при смене материала
- Регистрация через хранимую процедуру `sp_add_storage_unit`
- Toast-уведомление и обновление главного экрана

**Оптимизация** (client, admin)

- Сетка 2×2 с прогресс-барами загрузки всех четырёх складов
- Блок автоматических рекомендаций по перегруженным (>= 80%) и почти пустым (<= 20%) складам
- Вкладка «Перемещение» — выбор склада-источника и назначения, чекбоксы ордеров, операция `POST /api/transfer` (WMS)

**Утилизация просрочки** (admin)

- Выпадающий список порога устаревания: 7 / 14 / 30 / 60 / 90 дней
- Таблица с возрастом ордеров (красный > 60 дней, оранжевый 30–60), мастер-чекбокс выбора
- Списание выбранных ордеров с автоматической записью в `audit_log`

**Финансовый анализ** (client, admin)

- Топ-5 поставщиков по суммарному объёму поставок (количество поставок + сумма в рублях)
- Подсчёт поставщиков конкретного материала через `fn_count_suppliers_of_material` + список реквизитов через `fn_suppliers_of_material`
- Подсчёт поставщиков по городу банка через `fn_count_suppliers_by_bank_city` (регистронезависимое сравнение)

**Справочники** (просмотр — все роли, добавление — client, admin)

- Четыре вкладки: материалы / поставщики / единицы измерения / документы
- Полный список записей и форма добавления

**Инвентаризация** (все роли, WMS)

- Карточки складов с количеством позиций, суммарной стоимостью и возрастом самого старого ордера
- Сводная строка по всей системе
- Детальная таблица остатков выбранного склада с днями хранения, материалом, поставщиком, количеством и стоимостью

**Аутентификация и роли**

- JWT-токены со сроком действия 12 часов, подпись через `JWT_SECRET`
- Пароли хранятся как bcrypt-хэши (10 раундов)
- Самостоятельная регистрация (по умолчанию роль `client`); повышение до `admin` — только администратором
- Защита от случайного понижения собственной роли администратором
- На UI недоступные кнопки отображаются как `disabled` с подсказкой при наведении

## Архитектура

Многоуровневая архитектура с явным выделением четырёх логических слоёв:

```
┌──────────────────────────────────────────────────────────┐
│  Браузер пользователя                                     │
│  ┌──────────────────────────────────────────────────┐    │
│  │  React 18 SPA (тёмная тема)                       │    │
│  │  useState / useEffect / useCallback / Context     │    │
│  └──────────────────────────────────────────────────┘    │
└─────────────────────────┬────────────────────────────────┘
                          │ HTTPS / fetch
┌─────────────────────────▼────────────────────────────────┐
│  Docker host                                              │
│                                                           │
│  ┌─────────────────┐   /api/*     ┌────────────────────┐ │
│  │ wh66-frontend   │ ───proxy───▶ │  wh66-backend      │ │
│  │ nginx:1.27      │              │  Express.js + pg   │ │
│  │ статика React   │              │  JWT, bcrypt       │ │
│  └─────────────────┘              └─────────┬──────────┘ │
│                                             │ CALL/SELECT │
│                                   ┌─────────▼──────────┐ │
│                                   │  wh66-db           │ │
│                                   │  PostgreSQL 16     │ │
│                                   │  PL/pgSQL + триггеры│ │
│                                   │  volume: db_data   │ │
│                                   └────────────────────┘ │
└──────────────────────────────────────────────────────────┘
```

Ключевая особенность — выделение **слоя PL/pgSQL как самостоятельного уровня бизнес-логики**. Это сокращает сетевой трафик, обеспечивает атомарность связанных операций и гарантирует выполнение бизнес-правил независимо от способа обращения к данным.

Все три контейнера находятся в общей внутренней сети Docker и обращаются друг к другу по именам сервисов (`db`, `backend`, `frontend`). Извне доступны порты `5173` (frontend), `4000` (backend) и `5432` (PostgreSQL для прямого подключения при разработке).

## Установка и запуск

### Требования

- Установленный **Docker** и **Docker Compose**

### Запуск

```bash
git clone <repo-url> warehouse-66
cd warehouse-66
docker compose up --build
```

При первом запуске контейнер `wh66-db` автоматически прогонит четыре SQL-скрипта из `./db/` в алфавитном порядке (`01_` → `02_` → `03_` → `04_`). Контейнер `wh66-backend` ожидает `service_healthy` от базы через `pg_isready` и стартует только после полной готовности БД. Никаких дополнительных действий со стороны администратора не требуется.

Когда в логах появится строка `✓ Warehouse-66 API listening on http://localhost:4000`, открывайте в браузере:

**http://localhost:5173**

### Остановка и сброс данных

```bash
# Остановка (данные сохраняются в volume db_data)
docker compose down

# Полный сброс с удалением данных
docker compose down -v
```

После `docker compose down -v` следующий `docker compose up --build` снова прогонит все четыре SQL-скрипта и вернёт систему в начальное состояние.

### Локальный запуск без Docker

```bash
# 1. PostgreSQL: создать БД warehouse66, прогнать db/*.sql в порядке имён
psql -U postgres -d warehouse66 -f db/01_schema.sql
psql -U postgres -d warehouse66 -f db/02_package.sql
psql -U postgres -d warehouse66 -f db/03_triggers.sql
psql -U postgres -d warehouse66 -f db/04_seed.sql

# 2. Backend
cd backend
cp .env.example .env       # поправить PG-креды и JWT_SECRET
npm install
npm start                  # → http://localhost:4000

# 3. Frontend
cd ../frontend
npm install
npm run dev                # → http://localhost:5173, /api проксируется на :4000
```

## Учётные записи

При инициализации БД загружаются три тестовых пользователя — по одному на каждую роль (скрипт `05_users.sql`):

| Логин | Пароль | Роль | Доступ |
|---|---|---|---|
| `admin` | `admin123` | admin | Все операции, включая удаление, очистку журнала и управление пользователями |
| `manager` | `manager123` | client | Регистрация поставок, аналитика, добавление справочников, оптимизация |
| `viewer` | `viewer123` | guest | Только просмотр (карточки складов, журнал, справочники, инвентаризация) |

Самостоятельная регистрация через экран входа всегда создаёт пользователя с ролью `client`.

## База данных

### Основные таблицы

- **`suppliers`** — поставщики (ИНН, юр. адрес, банковские реквизиты)
- **`materials`** — материалы (код класса, код группы, базовая единица измерения)
- **`units_of_measurement`** — единицы измерения
- **`documents`** — типы сопроводительных документов (накладная, счёт-фактура, акт, УПД)
- **`storage_units`** — единицы хранения / ордера приёма (центральная таблица, ссылается на все справочники)
- **`audit_log`** — журнал операций, заполняется триггерами
- **`users`** — пользователи системы (`bcrypt`-хэш пароля, роль, отметка времени последнего входа)

Все внешние ключи определены с `ON UPDATE CASCADE` и `ON DELETE RESTRICT`. На `storage_units` заданы ограничения `CHECK (quantity > 0)` и `CHECK (unit_price >= 0)`.

### Пакет PL/pgSQL (`02_package.sql`)

Четыре объекта по заданию №66:

| Объект | Тип | Назначение |
|---|---|---|
| `fn_count_suppliers_of_material(p_material_code INT)` | function | Возврат `INT` — кол-во различных поставщиков материала. Защита `COALESCE` для пустого набора |
| `sp_add_storage_unit(...)` | procedure | 10 IN-параметров + 1 OUT (`order_number`). Внутренние проверки и `RAISE EXCEPTION` при ошибках |
| `fn_suppliers_of_material(p_material_code INT)` | function | `RETURNS TABLE` — поставщики с реквизитами и суммарным количеством, адреса через `CONCAT_WS` |
| `fn_count_suppliers_by_bank_city(p_city TEXT)` | function | Регистронезависимое сравнение через `LOWER()` + `EXISTS`-подзапрос на наличие приходов |

Дополнительно для WMS (`06_wms.sql`): `fn_inventory_by_warehouse(p_warehouse INT)` и `fn_inventory_summary()` — возвращают позиции и агрегаты по складу. Там же добавляется колонка `current_warehouse` в `storage_units` и связь `audit_log.user_id → users`.

### Триггеры (`03_triggers.sql`)

| Триггер | Событие | Действие |
|---|---|---|
| `trg_storage_audit` | AFTER INSERT / UPDATE / DELETE on `storage_units` | Запись в `audit_log` с типом операции и форматированным сообщением |
| `trg_materials_after_update` | AFTER UPDATE on `materials` | Каскадное обновление `unit_code` в `storage_units` при изменении в материале + фиксация в журнал |
| `trg_suppliers_before_delete` | BEFORE DELETE on `suppliers` | `RAISE EXCEPTION`, если на поставщика ссылаются приходные ордера |

### Инициализационные скрипты

Шесть скриптов выполняются при первом старте контейнера в алфавитном порядке:

| Файл | Содержимое |

| `01_schema.sql` | 5 таблиц + индексы + CHECK-ограничения |
| `02_package.sql` | Пакет PL/pgSQL: 3 функции + 1 процедура |
